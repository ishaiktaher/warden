# Deploying the authenticated control plane at warden.vouchins.com

The current Vercel project is intentionally a read-only showcase. The real
control plane must run from Warden's OCI image with durable PostgreSQL, Redis,
OIDC, signing, secret-custody and audit providers. Pointing DNS at a container
without those dependencies is not a production deployment.

## Repository support

- `deploy/production/` supplies a Kubernetes namespace, the hardened base
  deployment, two-replica topology, disruption budget, default-deny network
  policy and TLS ingress for `warden.vouchins.com`.
- `deploy-production-control-plane` is a manually approved GitHub Actions
  workflow. It accepts only an immutable image digest, verifies its GitHub
  provenance, runs a strict configuration preflight, runs the migration Job,
  performs a zero-downtime rollout, installs maintenance schedules and verifies
  the public readiness response.
- The GitHub `production-control-plane` environment should require a human
  reviewer. Its only cluster credential is `KUBE_CONFIG_BASE64`; prefer a
  narrowly scoped deployment identity rather than a cluster-admin kubeconfig.
- Release tags publish attested core, AWS, Azure and Google Cloud image
  variants. The core image includes the portable HTTPS and Vault adapters.
  PKCS#11 deployments need a hardware-specific image built from
  `requirements/providers/pkcs11.txt`.

## GitHub environment contract

Create the protected `production-control-plane` environment and require at
least one reviewer who cannot approve their own deployment.

Its only GitHub secret is:

- `KUBE_CONFIG_BASE64`: base64-encoded kubeconfig for an identity restricted to
  the `warden` namespace and the resource kinds used by the workflow.

Have a platform administrator apply `deploy/production/namespace.yaml` and
`deploy/production/deployer-role.yaml` once, then bind the Role to the GitHub
deployment identity. The RoleBinding is environment-specific and therefore is
not committed. The release identity cannot create, replace or delete namespaces
or RBAC policy.

Set these required GitHub environment variables:

- `WARDEN_SIGNING_PROVIDER`, `WARDEN_SECRETS_PROVIDER`,
  `WARDEN_AUDIT_PROVIDER`
- `CONTROL_PLANE_ALLOWED_EGRESS_HOSTS`
- `WARDEN_ALLOWED_ORIGINS`
- `WARDEN_PORTAL_ADMIN_GROUPS`
- `OTEL_EXPORTER_OTLP_ENDPOINT`
- `WARDEN_POSTGRES_EGRESS_CIDRS`, `WARDEN_REDIS_EGRESS_CIDRS`,
  `WARDEN_HTTPS_EGRESS_CIDRS`

Set the role variables `WARDEN_PORTAL_APPROVER_GROUPS`,
`WARDEN_PORTAL_AUDITOR_GROUPS`, and `WARDEN_PORTAL_RUNTIME_GROUPS`. Set only
the fields required by the chosen custody adapters:

- `WARDEN_SIGNING_PROVIDER_URL`, `WARDEN_SECRETS_PROVIDER_URL`,
  `WARDEN_AUDIT_PROVIDER_URL`
- `WARDEN_SIGNING_KEY_ID`, `WARDEN_SECRETS_PREFIX`, `WARDEN_AUDIT_TARGET`
- `WARDEN_PROVIDER_REGION`, `WARDEN_PROVIDER_MOUNT`,
  `WARDEN_PROVIDER_NAMESPACE`, `WARDEN_PROVIDER_LIBRARY`,
  `WARDEN_PROVIDER_TOKEN_LABEL`

The workflow rejects wildcard browser origins, non-HTTPS origins, missing
production controls, invalid network CIDRs and any CIDR that opens an entire IP
address family.

The three egress variables are destination network ranges, not host names.
Send HTTPS through a fixed-address egress proxy when OIDC, telemetry or cloud
provider endpoints do not have stable ranges. Keep the application-level host
allowlist in `CONTROL_PLANE_ALLOWED_EGRESS_HOSTS`; both controls must pass.

## Kubernetes secret contract

Create secrets through an external-secrets controller. The deployment workflow
checks their presence and required keys but never reads or prints values.

- `warden-runtime`: `DATABASE_URL`, `REDIS_URL`,
  `CONTROL_PLANE_ADMIN_KEY`, `WARDEN_OIDC_ISSUER`, and
  `WARDEN_OIDC_AUDIENCE`. Add `WARDEN_PROVIDER_AUTH_TOKEN` when the selected
  provider needs a bearer token, Vault token or HSM PIN. Add SMTP credentials
  only when approval email is enabled.
- `warden-migration-runtime`: a `DATABASE_URL` for a short-lived database role
  with DDL authority. Application credentials should not have DDL authority.
- `warden-vouchins-tls`: `tls.crt` and `tls.key`, preferably reconciled by
  cert-manager rather than entered by hand.

`CONTROL_PLANE_ADMIN_KEY` is a high-entropy break-glass credential generated by
the operator or secret manager. It is not a browser login and is ignored for
normal production API authentication. Rotate it after bootstrap and any use.

## External prerequisites

1. Provision PostgreSQL and Redis with TLS, backups and restore monitoring.
2. Configure the production OIDC application and required tenant, role and
   on-behalf-of claims. Browser management sessions also need a `groups` claim
   mapped to the configured portal groups; no group receives an administrative
   role by default.
3. Select any supported KMS/HSM, secrets and immutable audit provider. Mixed
   providers are supported.
4. Create `warden-runtime` and `warden-migration-runtime` through an external-secrets
   controller. Do not commit either Secret.
5. Configure custody-provider metadata and connector egress hosts as reviewed
   GitHub environment variables. Configure
   `WARDEN_ALLOWED_ORIGINS` with explicit HTTPS customer application origins
   when serving the embedded Connect component.
6. Install an ingress controller and certificate issuer; create or automate the
   `warden-vouchins-tls` Secret.
7. Review the rendered NetworkPolicy ranges for PostgreSQL, Redis and the
   HTTPS egress proxy. The checked-in ingress rule expects the ingress
   controller in the `ingress-nginx` namespace; change that selector if needed.
8. Move `warden.vouchins.com` DNS from the showcase deployment to the ingress
   only after staging, tenant-isolation and recovery tests pass.

## Release

Create a `vX.Y.Z` tag to publish an attested GHCR image. Review its provenance
and choose the digest whose dependency variant matches the selected provider.
Run **deploy-production-control-plane** with that digest. The workflow promotes
that exact digest in this order:

1. Validate the digest and verify its GitHub attestation.
2. Verify cluster secrets and apply non-secret configuration.
3. Apply the reviewed egress policy.
4. Run strict production preflight using the release image.
5. Run the schema migration using the separate DDL credential.
6. Roll out the two application replicas and wait for readiness.
7. Install reconciliation and audit-anchor CronJobs.
8. Verify the public health and readiness endpoints.

If a preflight or migration fails, the workflow prints the failed Job log and
does not alter the running Deployment.

## Go-live evidence

Before changing DNS, retain evidence for:

- OIDC administrator/approver/auditor group mapping and default-deny tests
- cross-tenant isolation and authorization tests
- provider conformance, audit retention and signing-key checks
- PostgreSQL backup restore and Redis/provider failure drills
- migration rehearsal and application rollback using the previous digest
- load, latency, error-rate and alert-routing acceptance
- TLS, WAF/DDoS, egress-proxy and external penetration-test review

Keep the Vercel deployment as a credential-free, read-only product showcase.
The authenticated test/management portal is part of the containerized control
plane and must never be pointed at the Vercel entrypoint.

DNS, OIDC, cloud resources, provider credentials and production approvals are
external authority and therefore cannot be created by this repository alone.
